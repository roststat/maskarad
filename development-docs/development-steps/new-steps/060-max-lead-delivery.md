# 060 — Доставка заявок в MAX

## Решения владельца

12 октября 2026 года: «Нужно сделать прием заявок с сайта, проверь формы и все приемщики. Давай заявки сделаем с получением в телеграм».

Уточнение владельца: «чтобы не было трансграничной передачи можем сделать в макс».

Уточнение заменяет Telegram на MAX. Закрытое серверное хранилище и защищённая страница владельца сохраняются как резервный контур: MAX не должен становиться единственной копией заявки.

## Проверенное основание выбора

- Официальный MAX Bot API поддерживает `POST https://platform-api2.max.ru/messages` с `chat_id` для закрытого чата или `user_id` для личного диалога.
- Официальная политика ООО «МАХ» указывает, что информация обрабатывается и хранится на территории Российской Федерации, а трансграничная передача персональных данных пользователей не осуществляется.
- Создание бота доступно после подключения и верификации профиля ИП на платформе MAX для партнёров; токен появляется после успешной модерации бота.

Источники: `https://dev.max.ru/docs-api/methods/POST/messages`, `https://legal.max.ru/pp`, `https://dev.max.ru/docs/chatbots/bots-create/create` (проверены 12 октября 2026 года).

## Подшаги

1. Проверить все формы и приёмщики. Доказательство: обычная форма и окно организатора отправляют данные только в общий `/api/leads`; других публичных маршрутов заявки нет.
2. Добавить серверную доставку в MAX Bot API без токена и ID получателя в репозитории. Доказательство: синтетический тест проверяет адрес метода, заголовок авторизации, личный/групповой получатель, состав сообщения и обработку ответа MAX.
3. Сохранить сначала локальную резервную копию, затем отправлять уведомление в MAX. Доказательство: API различает ошибку хранилища и ошибку MAX, не сообщает об успешной доставке при сбое настроенного канала.
4. Обновить описание потока данных и эксплуатационную инструкцию. Доказательство: политика, согласие, README и проверка серверной конфигурации перечисляют ООО «МАХ» и новые закрытые переменные.
5. Создать бота, добавить его администратором в закрытую группу, настроить production через `MAX_CHAT_ID`, проверить синтетическую заявку и только после этого публиковать. Доказательство: тестовое сообщение получено в нужной группе MAX, серверное хранилище содержит ту же синтетическую заявку, реальные данные и секреты в отчёт не попадают.

Все пять подшагов завершены 12 октября 2026 года. Итог: [060-max-lead-delivery.md](../../reports/060-max-lead-delivery.md).

## Границы

- Секреты задаются только как `MAX_BOT_TOKEN` и ровно один из `MAX_CHAT_ID`/`MAX_USER_ID` в закрытой конфигурации процесса.
- Для production по решению владельца используется закрытый `MAX_CHAT_ID`; положительный ID личного диалога не используется. Токен и ID в документацию не записываются.
- Бот используется только в закрытом личном диалоге или закрытой группе владельца; публичный канал для заявок не подходит.
- Содержимое заявки не записывается в журнал ошибки MAX и не используется в тестах.
- Отключать проверку TLS нельзя. Если сервер не доверяет сертификату `platform-api2.max.ru`, нужно установить официальный корневой сертификат Минцифры по инструкции MAX.
- До включения актуализировать сведения оператора о передаче данных российскому получателю и утвердить новую версию публичных документов. Техническая готовность сама по себе не подтверждает выполнение всех обязанностей оператора.
- Публикация и отправка тестового сообщения требуют отдельной закрытой настройки production и не выполняются с вымышленными реквизитами.
