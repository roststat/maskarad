# Технический SEO-аудит «Маскарада»

Дата: 12 октября 2026, Europe/Moscow. Сайт: https://maskarad-teatr.ru/.
Запрос владельца: «Сделай seo аудит моего сайта, только по технической части что улучшить и что добавить, чтобы сайт был максимально оптимизирован».

## Вывод

База индексации работает. Основные подтверждённые проблемы: битая ссылка, 13 страниц без входящих ссылок из других проверенных страниц, медленный мобильный LCP главной и каталога. Дополнительно нужны консолидация www и исправление Open Graph корпоративной посадочной. Исправления приложения и публикация в этот аудит не входят.

## Метод и ограничения

- Выполнен обязательный sync-check; репозиторий синхронизирован с origin/main. Автоматический server healthcheck не настроен, публичный сайт проверен отдельно.
- GET всех 122 уникальных URL sitemap; 16 дополнительных адресов, включая внутренние ссылки, HTTP/www, слеш, UTM, 404 и Markdown.
- Разбор исходного HTML: title, description, canonical, H1, robots, ссылки/якоря, alt и JSON-LD. Граф ссылок построен по серверному HTML, без кликов по переключателям и без внешних ссылок. Это не доказательство отсутствия URL в индексе.
- Сверка с исходниками app/header-nav.tsx, landing-data.ts, seo.tsx, layout.tsx, sitemap.ts, globals.css и next.config.ts.
- Проверено 66 ресурсов: 65 внутренних ответили 200; внешний noscript-пиксель Метрики не ответил в curl. Это не доказательство поломки счётчика, его работа не была предметом аудита.
- Lighthouse 13.5.0, headless Chrome, mobile, simulated throttling: RTT 150 ms, throughput 1638.4 Kbps, CPU ×4. По одному успешному запуску на четыре шаблона; без параллельных Lighthouse. Ошибочный пробный URL статьи дал 404 и исключён; итоговая статья взята из sitemap.
- Нет данных из кабинетов Вебмастера/Search Console, серверных логов поисковых роботов и CrUX. Не проверены фактическая индексация, выбранный поисковиком canonical, полевой INP и стабильность доступности за период. Разбор HTML не заменяет полный W3C/Schema.org validator.

## Подтверждённые проблемы и исправления

### P1 — битая внутренняя ссылка

`/prazdniki/novogodniy-detskiy-prazdnik` возвращает 404. В серверном HTML найдены три ссылки с двух страниц: `/dlya-vzroslyh` (одна), `/dlya-biznesa` (две). Адрес также прописан в app/header-nav.tsx и app/landing-data.ts.

Исправление: выбрать существующую релевантную новогоднюю посадочную отдельно по смыслу каждой ссылки; обновить источник навигации. Если ошибочный URL ранее использовался извне — добавить точный постоянный редирект на подходящую замену. Не перенаправлять автоматически на главную.
Приёмка: все внутренние назначения имеют 200 либо осмысленный прямой redirect, этот 404 больше не встречается в ссылках.

### P1 — 13 страниц без входящих HTML-ссылок с других проверенных страниц

Они присутствуют в sitemap, но недостижимы от главной по графу ссылок серверного HTML. Самоссылки и `#zayavka` не считаются входящими. Список:

- `/dlya-detey`
- `/dlya-vzroslyh`
- `/prazdniki/vypusknoy-v-detskom-sadu`
- `/prazdniki/vypusknoy-v-nachalnoy-shkole`
- `/prazdniki/vypusknoy-v-11-klasse`
- `/prazdniki/maslenitsa`
- `/prazdniki/vypusknoy-v-stile-fashion`
- `/uslugi/pozdravitelnaya-pesnya`
- `/uslugi/detskiy-tort`
- `/uslugi/shou-s-zhivotnymi`
- `/prazdniki/detskiy-prazdnik-na-teplohode`
- `/prazdniki/individualnyy-detskiy-prazdnik`
- `/prazdniki/obrazovatelnyy-detskiy-prazdnik`

В app/header-nav.tsx аудитории реализованы `<button>`; переключение показывает другой набор меню, но кнопки сами не ведут на посадочные аудитории. Sitemap помогает обнаружению, однако не заменяет ссылки.
Исправление: добавить обычные `<a href>` на аудитории и релевантные карточки/ссылки в каталогах праздников, услуг и подборках. Дать каждой нужной индексируемой странице путь от главной без взаимодействия с переключателем. Приёмка: 122/122 URL достижимы; у каждой вложенной страницы есть минимум одна входящая ссылка с другой страницы.

### P1 — мобильная загрузка главной и каталога

| Шаблон | Performance | LCP | CLS | TBT |
|---|---:|---:|---:|---:|
| Главная `/` | 74 | 6,4 с | 0 | 30 мс |
| Каталог `/spektakli` | 76 | 7,0 с | 0,041 | 20 мс |
| Корпоративная посадочная | 99 | 2,1 с | 0,041 | 10 мс |
| Статья `/stati/igrovoy-scenariy-dlya-detskogo-prazdnika` | 99 | 1,8 с | 0,041 | 20 мс |

Это лабораторный снимок, не полевая оценка Core Web Vitals. TBT не равен INP. SEO Lighthouse = 100 у всех четырёх, что не обнаруживает все проблемы полного графа сайта.

Конкретный ресурс: `/images/legacy/maskarad-mask-transparent.png` — 702 725 байт в Lighthouse; CSS `.eyebrow::before` использует его для значка 1,35 × 1,15 rem. Только для него Lighthouse оценивает экономию около 440 556 байт. Для изображений главной суммарная оценка экономии 539 KiB. Объём передачи главной в замере — около 1061 KiB.

Исправление: изготовить маленькую прозрачную WebP/AVIF-версию маски под фактический размер и DPR, использовать её в CSS; подобрать размеры/качество изображений галерей. Далее исследовать задержку отрисовки hero по trace: high fetchpriority/eager и обнаружение hero в HTML уже есть, добавлять preload вслепую не требуется. После изменений повторить замеры в одинаковых условиях; не обещать экономию LCP только на основании веса PNG.

Цель: полевой p75 LCP ≤2,5 с, INP ≤200 мс, CLS ≤0,1, отдельно mobile/desktop. Добавить сбор Web Vitals без персональных данных и контроль регрессий. При появлении РСЯ резервировать размеры рекламных контейнеров и повторно измерить CLS/LCP.

### P2 — www отдаёт копию сайта с 200

`https://www.maskarad-teatr.ru/` и `/spektakli` возвращают 200; canonical корректно указывает на non-www. `http://www.../` перенаправляется 301 на HTTPS www, где остаётся копия. HTTP non-www и завершающий слеш перенаправляются корректно.

Исправление: настроить серверный 301/308 со всех www-адресов сразу на HTTPS non-www с сохранением пути и query. Canonical уже помогает консолидации, поэтому это не доказанная проблема двойной индексации. Приёмка: один переход на выбранный домен; корректный сертификат обоих имён.

### P2 — неверный Open Graph корпоративной страницы

`/prazdniki/korporativnyy-novogodniy-prazdnik` имеет свой title/description/canonical, но наследует `og:url`, `og:title`, `og:description` и Twitter-описание главной. Подтверждено HTML и наследованием metadata.

Исправление: явные Open Graph/Twitter поля корпоративной страницы, подходящее изображение. Это прежде всего исправление превью при отправке ссылки; не следует обещать прямой прирост позиций.

### P2 — слишком широкий резервный redirect старых URL

Проверочный несуществующий `/detskii-prazdnik/__seo-audit-not-found-20261012` даёт 308 на `/spektakli`. В next.config.ts есть широкие правила для старых разделов. Для известных исторических адресов они могут быть оправданы, но неизвестные пути тоже превращаются в перенаправления на общий каталог.

Исправление: сохранить подтверждённые релевантные старые переходы, проработать карту миграции; неизвестным URL без замены возвращать 404/410. Возможность soft 404 — риск, а не подтверждённый статус в кабинете поисковика.

## Что добавить в технический контроль

1. Полный crawl gate всех sitemap и найденных HTML-ссылок: 4xx/5xx, редиректы, canonical, noindex, дубли, входящие ссылки. Текущие smoke-проверки пропустили подтверждённый 404 и страницы без входящих ссылок.
2. Контракт metadata для каждого маршрута: canonical/OG URL, непустые уникальные title/description, корректные размеры social image.
3. Регрессионные бюджеты изображений и Lighthouse для четырёх шаблонов; полевые Web Vitals и мониторинг HTTPS/доступности. Не добавлять новое расписание без запроса владельца.
4. Единый источник реальной даты изменения URL для sitemap и Article/WebPage. Сейчас у 45 Article даты совпадают с sitemap, будущих lastmod нет. Это укрепление процесса, не найденная ошибка всех дат.
5. Дополнить Organization полем logo и подтверждёнными sameAs, если есть официальные профили. Не добавлять фиктивные адреса, рейтинги, Product/Event ради количества схем. Для реального видео — VideoObject после появления необходимых данных.
6. Для статичных картинок можно задать более длинный cache-control вместе с версионированием имени. Прямые `/images/...` сейчас имеют `max-age=0`; это revalidation, а не отсутствие кеша. JS/CSS уже имеют годовой immutable-кеш, gzip работает.

## Что уже работает

- Все 122 URL sitemap: HTTP 200, один H1, правильный self-canonical, нет noindex, уникальные непустые title/description.
- Основное содержимое и FAQ доступны в исходном HTML. Все 122 FAQPage содержат пять вопросов; вопросы/ответы совпали с текстом HTML. JSON разбирается; битых якорей заявок не найдено. Это техническая проверка, не проверка достоверности каждого факта.
- Organization/WebSite — 122, BreadcrumbList/WebPage — 121, Service — 60, Article — 45, ItemList — 3. Отсутствие отдельного WebPage на главной само по себе не критическая ошибка.
- Нет изображений без атрибута alt в проверенном HTML; это не означает оценку качества каждого alt.
- Произвольные новые URL вне исторических catch-all возвращают настоящие 404.
- robots.txt доступен и ссылается на sitemap; CSS/JS не заблокированы. Юридические страницы доступны и имеют noindex, follow. Админский маршрут в исходниках задаёт X-Robots-Tag noindex/nofollow; авторизованные данные не запрашивались.
- UTM-вариант главной имеет canonical без параметра. Markdown `/markdown/spektakli/zolushka` имеет HTTP Link rel=canonical на HTML; отсутствие noindex само по себе здесь не ошибка.
- HTML/JS/CSS сжимаются gzip, статические чанки кешируются. TLS при HTTPS-запросах прошёл штатную проверку. Малый curl TTFB в этой сети не доказывает быстрый LCP на телефоне.

## Актуальность FAQ и «стандартов для ИИ»

FAQ остаётся полезным элементом страницы, JSON-LD можно сохранять согласованным. Но Google прекратил показывать FAQ rich results с 7 мая 2026, а в июне удалил соответствующую документацию. Наращивание FAQ schema не следует считать рычагом получения этого расширенного сниппета. Google также разъясняет, что llms.txt не улучшает и не ухудшает видимость в его поиске. Приоритет — доступные ссылки, скорость, корректные URL и настоящие данные.
